任务拆解 / 售后 · 判责 · 可信闭环

售后 Agent 的价值，是让事情真正往前走

会解释、能执行、能判责与能闭环，是四个不同的产品问题。

内容摘要 售后 Agent 需要区分解释、执行、判责与闭环。安装咨询、质量凭证与工单接续分别要求不同事实、授权和完成证据；草稿、提交与处理完成应保留各自的状态。

“已帮您催促”不等于创建了催办记录；展示预约入口，不等于完成预约；收集完凭证，也不等于完成责任判断。

用户问的是一句话，产品要处理的是一件事。我更愿意把售后 Agent 理解为：在适用规则与商家授权内，基于可核验事实，完成下一步，并让处理状态能够被查询和接续。

先分清当前承担哪一段任务

“申请退款”可能是引导用户进入申请，也可能是获授权后执行处理。名字相似，操作主体、权限和完成证据却不同。自动化程度应由这些事实决定，不能由功能名字决定。

同样，能编排流程不等于有业务动作；有动作不等于当前已授权；已授权也不等于业务系统已经接通。“可执行”需要业务允许、系统可达、结果可核验同时成立。

安装咨询与预约办理，走两条轨道

规则与资料咨询依赖订单的办理
是否包安装、收费方式、型号视频、尺寸与拆旧说明核对订单、安装权益与当前服务状态，进入适用的办理流程
未必需要先选择订单需要业务对象和执行授权

知识与办理共同服务用户，不是有了智能策略就要把知识轨道全部替换。收费、权益与联系时效还必须保持一致，不能知识解释一种、执行流程又采用另一种。

看见破损，还没有完成判责

识别图片里的现象，与作出有业务后果的责任判断，是不同能力。发生时间、物流状态、商品特点、售后规则和凭证完整性，都可能影响后续处理。

流程优化可以减少重复确认、补齐步骤，但不能提供缺失的事实。证据不足、规则不清和需要人工判断，都应该是系统可以保留的真实状态。

证据不足

说明还缺什么，整理已有材料，再进入补充或接续。不要为了走完流程补出一个确定结论。

没有执行授权

完成能够承担的查询和说明，把后续任务交给有权限的处理者。不能从历史处理习惯推断退款或补偿权限。

无法确认执行结果

先核对实际业务状态，再判断是否重试。没有收到返回，不等于没有执行。

草稿、提交与完成，需要各自的证据

草稿信息已准备，尚未正式提交
已提交申请已创建，可能仍在等待处理
处理中按真实状态继续接续
已完成承担的任务达到可确认结果

通知只是提醒，不能代替订单或工单结果；聊天里说“成功”也不是业务证据。重复进入服务时，需要从现有状态继续，避免重复创建和重复承诺。

人工接续也属于闭环。查到了什么、收集了什么、尝试了什么、为什么不能继续，都应随未完成任务一起交接。

归因的目的，是找到谁能改变问题

用户一开始就要求人工，与回答多轮仍未解决，应分开观察。配置拦截、知识缺失、已有知识未被召回、执行失败和必要人工判断，也不能交给同一种修复动作。

分析完整会话要检查相关轮次，定位触发原因要回到触发轮次与此前上下文。知识是否存在，还要检查答案、生效条件、实际版本与召回记录，不能只凭最后一句文本猜原因。

自主解决的代理口径，不等于任务完成

如果“自主解决”仅以未转人工估算，它仍然只是代理指标。没有转交的会话，可能仍未完成任务。我要继续看能力是否触发、动作是否成功、状态能否确认，以及满意度、重复进线和风险有没有恶化。

策略迭代也一样。历史问题可以形成候选修正，但还需要适用条件、证据、冲突检查与回放验证，不能因为文字像正式规则就直接生效。

先把能够承担的部分做可靠，把不能承担的部分交接清楚，再用真实结果扩大可信服务的范围。
